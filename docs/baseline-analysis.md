# Baseline Network Traffic Analysis

## 1. Objective

Establish a baseline of normal network activity by capturing and examining traffic generated by a Linux workstation. The purpose is to identify common network protocols, understand communication patterns, and document observable behavior before investigating potentially suspicious activity.

## 3. Protocols Observed

The following protocols and communication patterns were identified:

- **DNS:** Domain name queries and responses, including A, AAAA, and HTTPS resource records.
- **TCP:** Connection establishment, acknowledgments, data exchange, and connection termination.
- **HTTP:** An HTTP GET request and an HTTP 204 response.
- **TLS:** Client Hello messages, Server Hello messages, and encrypted Application Data.
- **QUIC:** Initial packets and cryptographic handshake-related information, consistent with QUIC-based communications.

## 4. Key Observations

### 4.1 DNS Activity

DNS queries and responses were observed for several domains, including:

- `connectivity-check.ubuntu.com`
- `api.snapcraft.io`
- `example.com`
- `raw.githubusercontent.com`
- `mobile.events.data.microsoft.com`

The analysis identified corresponding DNS transactions using transaction IDs and source/destination ports.

The `example.com` lookup included HTTPS (type 65), AAAA (type 28), and A (type 1) queries. The HTTPS record advertised ALPN protocols `h3` and `h2`.

### 4.2 TCP Activity

TCP connection handshakes and bidirectional data exchanges were observed.

The analyzed streams demonstrated successful connection establishment and data transfer. FIN and RST flags were also identified.

Some streams contained retransmission, duplicate ACK, and out-of-order indications. These observations alone are insufficient to determine whether packet loss or network problems occurred.

### 4.3 HTTP Activity

An HTTP request to `connectivity-check.ubuntu.com` was identified:

- Request: `GET / HTTP/1.1`
- Destination port: 80
- Response: `HTTP/1.1 204 No Content`
- Response header: `x-networkmanager-status: online`
- Observed response time: approximately 197 milliseconds.

This communication is consistent with an Ubuntu network connectivity check.

### 4.4 TLS and QUIC Activity

TLS Client Hello messages exposed server names through the Server Name Indication (SNI) extension.

Observed server names included:

- `api.snapcraft.io`
- `mobile.events.data.microsoft.com`
- `raw.githubusercontent.com`

Encrypted Application Data records were observed after TLS negotiation.

QUIC Initial packets were also identified. Their presence is consistent with applications using QUIC, which is the transport protocol used by HTTP/3.

The encrypted payloads could not be interpreted from this capture alone.

## 5. Limitations

- The capture represents approximately 20 seconds of network activity and is not a complete representation of the workstation's network behavior.
- Encrypted TLS and QUIC payloads limited application-level inspection.
- SNI identifies the requested server name but does not independently establish the legitimacy of the server or communication.
- Retransmission and out-of-order indicators do not independently prove packet loss or malicious activity.
- No individual packet or connection should be classified as malicious based solely on the observations documented here.

## 6. Conclusion

The baseline capture contains DNS, TCP, HTTP, TLS, and QUIC traffic consistent with ordinary workstation network activity.

The HTTP connectivity check explicitly reported the workstation as online. Several application-related domain names were also observed during the capture.

No confirmed malicious activity was established from this baseline analysis.

This capture will serve as a reference point for comparison during subsequent suspicious network activity investigations.
